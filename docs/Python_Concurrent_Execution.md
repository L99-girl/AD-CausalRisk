# 四阶段并发、重放与失败处理

课程Python服务按`runId`协调同步执行。同一请求的多个并发POST共享一次四阶段计算，返回内容和第一次实际阶段耗时一致。不同`runId`可以独立执行，慢计算期间仍可读取已完成结果。接口没有后台任务、取消操作或实时阶段进度。

| 场景 | 行为 |
| --- | --- |
| 同runId、相同语义JSON，已完成 | 返回缓存副本，保留原耗时；JSON对象键顺序不影响请求摘要 |
| 同runId、相同请求，正在执行 | 等待原执行；成功共享结果，失败共享HTTP500，不再次调用工作流 |
| 同runId、不同请求，已完成或执行中 | HTTP409/RUN_ID_CONFLICT；不覆盖、不启动另一次执行 |
| 新runId，容量已满 | HTTP503/RUN_CAPACITY_REACHED；容量包含完成记录和执行中唯一runId |
| 满容量时已有runId的相同请求 | 仍可读取缓存或等待原执行，不额外占用容量 |
| 查询执行中runId | HTTP404/RUN_NOT_FOUND；GET只查询完成缓存，404不能证明没有执行 |
| 工具异常或完整结果校验失败 | HTTP500/ASSESSMENT_FAILED；无成功缓存，唤醒所有等待者并释放容量 |
| 失败结束后新的显式POST | 可重新尝试；Python不自动重试，Java应保留失败与未知执行记录 |
| 质量BLOCKED | 共享原null/UNAVAILABLE，只保留实际执行的DATA_FUSION，不调用评分器 |

缓存在登记、查找与提交期间持锁；计算、校验、复制和等待都在锁外。请求在计算或等待前取得快照。工作流返回先复制再校验，并将通过校验的同一对象提交为完成结果。调用方各自获取副本，不能修改其他调用方或缓存的图、说明和分数。

POST仍同步执行。调用方超时或断线不会取消计算；应按[只读恢复流程](Python_Interop_Recovery.md)查询原runId并核对Java业务历史。不能因为超时或执行中404就另造runId重算。缓存重启清空，不具备持久任务、权限或业务幂等能力。当前容量约束用于本地演示，不代表生产吞吐、服务时限或多进程协调已验收。

认知/MRI的`number`字段按精确数值判断重放身份：`25`与`25.0`、`0`与`-0.0`共享原执行及缓存。该比较不舍入、不加容差；相邻浮点即使最终同分也属于不同输入。日期、版本、数组顺序、缺字段与显式null仍各自保留；APOE计数和窗口的严格整数校验仍先执行。身份摘要只用于请求绑定与共享执行，首个请求的实际值/类型、发送字节、原内容摘要、来源引用和阶段输入改写检查均不归一化。

原共同契约、字段、版本、24个月规则、图门控、贡献和BLOCKED语义保持。排序仍为合成演示，并发保证不认证临床精度。

在仓库根目录、安装`requirements-dev.lock`的环境运行：

```powershell
python -m unittest discover -s tests -p test_course_concurrency.py -v
python -m unittest discover -s tests -v
```

专项验证使用事件控制慢执行，覆盖独立POST/GET、即时409/503/404、重复成功/失败共享、容量释放、线程中断、输入/结果隔离、BLOCKED及自有临时HTTP，无需研究数据或现有服务。
